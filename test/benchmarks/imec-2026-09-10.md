# Imec query-engine benchmark — 2026-09-10

## Conclusion

The SQLite resolver is benchmarkable, but is not yet a drop-in replacement for
imec's installed resolver. Real project queries expose missing primitive-array
`includes` support and different default string ordering. Small resident-object
queries generally favor the JavaScript engines. SQLite wins some larger structural
queries, but deep offsets, JSON predicates and full payload projections need work.

## Scope and method

- Imec commit: `9d6ab92a4afb6f34af3f1d6d35b0cff7303e2b7b`; project left unchanged.
- Baseline: the actual installed `alinea@8381726`, including
  `patches/alinea-pr-554.patch`, not this branch's legacy resolver.
- Sync engine: `303001ad6951ee02c29a8330c76d49bc2226a726`, exported from Git.
- SQLite: query/runtime code at `3bc133eb` (query implementation unchanged from
  `5273296e`). No engine optimization or compatibility fixes made for this test.
- Bun 1.4.0 on macOS arm64. Native means Bun's SQLite driver, not Node's driver.
  WASM means `@alinea/sqlite-wasm` under Bun, **not a browser measurement**.
- The actual imec schema is bundled with a config-only `createCMS` shim.
  CSS is omitted. Next.js, caches, tracing backends, auth and remote services
  are not executed. Source reading uses Alinea's FSSource, not an application
  JSON-reading workaround.
- 11,374 normalized entry versions, 61,486,398 bytes of normalized field JSON.
  Default published queries return 11,373 entries.
- SQLite is populated with the installed engine's normalized rows to isolate
  query execution from normalization differences. All SQL payloads are resident.
  This is **not** a full release-builder or browser lazy-transfer benchmark.
- Sync engine independently exports the same source through its runtime exporter;
  frames use no compression and hydrate from an in-memory encrypted bundle.
- Engines execute in separate processes, sequentially. Per case: first execution,
  five warmups, 30 timed executions. Timers include resolver planning and result
  construction, not result hashing/serialization or fixture loading.
- A first pass was followed by a second pass with explicit binary-order
  diagnostics. Tables below use the second pass, not the best run.
  First-query and p95 values are retained in the accompanying JSON.
- Equality means SHA-256 of recursively key-sorted JSON results, preserving array
  order. A different result is not counted as an equivalent-query speedup.
- Shared configuration uses the installed schema implementation. Sync-engine
  support dependencies come from the current workspace where unavailable in imec;
  this is a branch-resolver comparison, not a historical locked deployment.
- These are exploratory microbenchmarks, not statistically isolated production
  capacity measurements. No browser networking, concurrency, write, search,
  vector, true cold-start or retained-memory conclusion is supported.

## Correctness findings

1. SQL article cards fail on `visibility: {includes: 'international'}`.
   `Condition.ts` sends the primitive operand to `compileFilter`, which requires
   an object. The installed engine accepts this actual project query.
2. Installed default string sorting uses `localeCompare(..., {numeric: true})`;
   SQL uses binary ordering and currently ignores the distinction requested by
   `caseSensitive`. Seven sorted baseline cases differ. All seven explicit
   binary variants match across all four runners.
3. Sync-engine differs from the installed engine on nested navigation (first
   observed difference `$.children.0.title`) and article cards
   (`$.5._id`). Their root causes have not been established by this benchmark.
   Do not interpret those timings as proven equivalent behavior.
4. Native and WASM agree on every successful query in this run.

## Setup observations, not an apples-to-apples startup ranking

The second run took about 0.763 s to scan/build the installed index **and export
the benchmark row fixture**. Sync source scan/export/store construction took
1.104 s. SQL materialization from already-normalized JSON took 2.072 s and
produced a 132,546,560-byte query database including FTS.

Reopening the freshly built native file took 0.782 ms; reading the complete file
and opening WASM took 41.964 ms. The OS cache was warm. Sync's 0.684 ms store
constructor receives an already-decoded index; it excludes index parsing.
None of these figures establish a fair cold-start comparison.

Memory snapshots were deliberately excluded from the checked-in results: the
benchmark retains setup fixtures and different temporary artifacts per engine,
so those readings do not represent comparable steady-state engine memory.

## Reproduce

Run from the Alinea worktree. Use a fresh scratch directory each time.
The archive and module link below write only to scratch; imec remains read-only.

```sh
bench_dir=$(mktemp -d /private/tmp/alinea-imec-bench-XXXXXX)
mkdir "$bench_dir/sync"
git archive 303001ad6951ee02c29a8330c76d49bc2226a726 | tar -x -C "$bench_dir/sync"
ln -s /Users/ben/projects/codeurs/imec-rebuild/node_modules "$bench_dir/node_modules"
bun test/benchmark-imec.mjs /Users/ben/projects/codeurs/imec-rebuild "$bench_dir" "$bench_dir/sync"
bun test/benchmark-imec-run.mjs /Users/ben/projects/codeurs/imec-rebuild "$bench_dir" installed 2
bun test/benchmark-imec-run.mjs /Users/ben/projects/codeurs/imec-rebuild "$bench_dir" sqlite 2
bun test/benchmark-imec-run.mjs /Users/ben/projects/codeurs/imec-rebuild "$bench_dir" wasm 2
bun test/benchmark-imec-run.mjs /Users/ben/projects/codeurs/imec-rebuild "$bench_dir" sync 2
```

Scratch contains private normalized content, complete query results and the
database; do not publish it. Checked-in results contain timings/counts/hashes only.
The scripts log process memory for diagnostics; do not compare those as engine
retained-memory measurements.
